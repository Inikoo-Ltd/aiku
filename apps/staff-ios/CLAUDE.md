# staff-ios

Native iOS staff app for aiku, covering the warehouse flow. It uses Swift 6 and SwiftUI, targets iOS 17+, iPhone only, and its bundle id is `com.inikoo.aiku` (`com.inikoo.aiku.dev` for Debug).

The Laravel, PHP, Vue and Pest rules in the aiku root do not apply here.

## Project

- The Xcode project is generated by XcodeGen from `project.yml`. `Aiku.xcodeproj` and `Aiku/Resources/Info.plist` are gitignored: never commit them and never edit them by hand.
- Run `xcodegen generate` after pulling and after adding, moving or deleting a Swift file, or the file is not compiled.
- Build settings live in `Config/*.xcconfig`. `Config/Signing.xcconfig` (signing team) and `Config/Local.xcconfig` (API URL for a physical device) are per developer and gitignored; copy them from their `.example` files.
- Write `//` as `/$()/` inside xcconfig values, otherwise the rest of the line is a comment.

## Sample data

Most screens still run on sample data so developers can see each screen before it is wired to the API.

- Each area keeps its sample data and its `@Observable` store in `Features/<Area>/Models/` (Foundation only, no SwiftUI).
- When a screen is wired to real data, remove the sample data it no longer uses.
- Wired to the API so far: sign in (with two-factor, same flow as aiku_droid: the authenticator code step on `otp_required`, and in-app setup on `two_factor_setup_required` with the otpauth link, an on-device QR code and the setup key, confirmed by sending `one_time_password` with `two_factor_setup_token` to `mobile/login`), sign out, profile (`mobile/profile`), permissions, change password and the code-based password reset (`mobile/password*`, same flow as aiku_droid), Goods out delivery notes (list, backlog counts, picking, packing, shipments, finalise, dispatch, documents, and changing an SKO's wholesale or dropshipping picking location through `PATCH mobile/location-org-stocks/{id}` with only the priority flags) through `mobile/warehouses/{w}/delivery-notes` and `mobile/delivery-notes/{id}`, picking sessions, staff chat (Ask CRM, `ShellRoute.staffChat` with kind `delivery_note` or `picking_session`), the Scan tab lookup (`mobile/warehouses/{w}/scan`), and Clocking (status, timesheets, QR clocking with camera and location, adjustment requests, clocking notes, leave list and leave requests, adjustment cancel, leave and adjustment attachments) through `mobile/clocking`, and Inventory (dashboard, SKO list and filters, the negative stock bucket as one row per SKO-location with that location's quantity, opening the SKO in that location, SKO detail with audit, move, consume, add and remove locations, stock history per SKO) through `mobile/warehouses/{w}/inventory-dashboard`, `mobile/warehouses/{w}/org-stocks` and `mobile/location-org-stocks`, My work and its badges (`mobile/warehouses/{w}/my-work` and `mobile/warehouses/{w}/badges`: the My work tab count, and the unassigned count on the Goods out shortcut and Backlog menu entry), the Inbox (`mobile/inbox`: work notifications as the server sends them, read, unread and read all, opening the record and switching warehouse when needed; the tab badge from `inbox_unread` on the badges or `mobile/inbox/unread-count`, cleared on sign out), the Warehouse dashboard (`mobile/warehouses/{w}/dashboard`: blocks the user has no right to come back null and are hidden; each count opens its list already filtered to that bucket or state), Search (`mobile/warehouses/{w}/search`: type chips only for the `types` the server sends, debounced with Show more paging per type, results open the same screens as Scan, recent searches per user and warehouse on the device), the clocking status and this week's hours on Home and the clocking line in the Menu (from `mobile/clocking`, cleared on sign out), and Fulfilment (pallet deliveries, stored pallets and incidents, stored items and their audits, pallet returns with picking, shipments and dispatch) through the mobile fulfilment inbound, storage and outbound routes.

## Backend

- The app talks to aiku only through the staff API, never the database.
- Debug builds call `http://aiku.test/app/api`, Release builds `https://aiku.io/app/api` (`API_BASE_URL`, read at runtime from `AikuAPIBaseURL` in Info.plist). On a phone, set `Config/Local.xcconfig` to the Mac's LAN address and run `php artisan serve --host=0.0.0.0 --port=8000`, because Valet only listens on 127.0.0.1.
- The app key goes in the gitignored `Config/Secrets.xcconfig` (copy `Secrets.xcconfig.example`), and so does `AIKU_SENTRY_DSN`, the key of the iOS Sentry project. Crash reporting (`Core/CrashReporting.swift`, the Sentry Swift package) starts only when that key is set and never under tests; reports carry no personal data, no screenshots or view hierarchy, and the user only by numeric id, as on Android.
- Sign in uses `POST mobile/login` and keeps the token in the Keychain (`Core/Auth`); `GET mobile/profile` gives the name, job title, job positions and organisation (the role shown is the lead job position, then the job title); `GET mobile/permissions` gives permissions and roles, cached by `PermissionStore`.
- Modules follow the user's rights exactly as the server sends them, never guessed on the device: `ModuleAccess` comes only from the selected warehouse's `can` abilities (`mobile/warehouses`); a signed-in user sees no warehouse module until those arrive (they are cached, so this only happens on the very first launch). Goods in shows when the user has `view_goods_in` or `view_returns`; Backlog and Stock deliveries need `view_goods_in`, Returns needs `view_returns`, as on Android. `Session.visibleModules` hides menu groups, Home shortcuts, section pills and the Scan tab the user can't open; the warehouse dashboard shows a block only when the server sends it (null means no right). Actions inside a screen follow the abilities the API sends with each record.
- Mobile routes sit under `/app/api/mobile` (`routes/api/grp/mobile.php`). They need the `X-Aiku-App-Key` header (one of the backend's `MOBILE_APP_KEYS`) and a Sanctum bearer token with the `mobile` ability; `login` returns the token.
- App Transport Security: `NSAllowsLocalNetworking` covers LAN IP addresses but not `.test` hosts.
- App version, as on Android: on launch and on every return to the app (at most every 10 minutes after an answer) `AppVersionStore` asks `GET mobile/app-version` and compares the `ios` codes with `CFBundleVersion`, which is `CURRENT_PROJECT_VERSION` in `project.yml` (raise it for every build that leaves a developer's machine). Below `minimum_version_code` the whole app is replaced by Update required; below `latest_version_code` Home shows a banner until it is dismissed for that version. The Update button opens `update_url`; without one the screen says to ask a supervisor. Offline or on an error nothing is blocked. The values come from `MOBILE_IOS_*` in the backend `.env`.

## Offline

Line-level work is saved on the phone while offline and synced to Aiku later (design v3, contract in `aiku_droid-work/phase8-offline-contract.md`), the same way as aiku_droid.

- `Core/Offline` holds it. `OfflineDevice` keeps the install's device id and the per-user sequence counter in the Keychain; `APIClient` sends `X-Aiku-Device`, `X-Aiku-Platform: ios` and `X-Aiku-App-Version` on every request, and `OfflineNetworkObserver` records the server `Date` (`ServerClock`) and keeps the last answer of each delivery note, return, stock delivery, location and SKO page per user (`OfflineDownloads`, prefetching assigned notes from My work and the returns being handled).
- `OfflineQueue` is a file in Application Support (file protection, excluded from backup) that survives sign out and 401; each action keeps its user and warehouse and syncs only under that user. `OfflineSyncEngine` numbers actions when they are first sent, posts `mobile/warehouses/{w}/offline/sync` in batches of 50, resends a missing earlier number as a void, refetches the records that changed and checks still-open outcomes with `mobile/offline/operations?state=open`. `OfflineWork` (main actor) watches the connection and syncs on reconnect, on return to the app, at clock out, every two minutes while work waits and right after an action is queued. There is no background sync while the app is closed yet.
- Online writes for pick, pick all, not picked, waiting and pack carry a `client_request_id`; when the phone is offline, or earlier work on the same note has not synced, they are planned against the saved copy with the queued work applied and queued instead (pick all becomes an explicit pick, a changed unsent pick replaces the queued one). Status changes stay online and first wait for the note's queued work to sync. Scan to pick matches the line barcodes offline.
- Offline & sync lists the queue per record with Undo; Resolve conflicts reads the open and recent operations and posts `resolve` or `rollback`. A user signing in on a phone holding someone else's unsent work sends `mobile/offline/waiting-notice` once per session.
- Goods in, returns, moves and counts already send through the same queue and endpoints on Android; on iOS only Goods out lines queue so far.

## Structure

- `App`: entry point, sign-in gate (`RootView`), signed-in navigation stack (`MainView`).
- `Core/Auth`: `AuthStore`, `AuthService`, Keychain token store.
- `Core/Navigation`: `AppRouter` (tabs and path) and one route enum per area in `Routes/`; `ModuleSections` drives the section pills under a module header.
- `Core/Theme`: the 11 Aiku themes, light and dark `Palette`, `ThemeStore`, `AikuColor` tokens.
- `Core/UI`: shared pieces. `AppScreen`/`ScreenScaffold` (header, scroll, footer, tab bar, toasts), `MainTabBar`, `ModuleTabs`, `AikuButton`, `StatusChip`, `Card`, `ListRow`, inputs, `.aikuSheet` and `.aikuConfirm`, `ToastCenter`, `InlineAlert`, `EmptyState`, skeletons, `CameraScanScreen`.
- `Core/Models`: Foundation-only shared types (`Tone`, `Chip`, `AppIcon`, `Session`).
- `Features/<Area>`: `Login`, `Shell` (Home, My work, Scan, Inbox, Menu, Profile, Appearance), `Inventory`, `Locations`, `GoodsIn`, `GoodsOut`, `Dispatch`, `Fulfilment`, `Clocking`, `System` (Offline & sync queue, Resolve conflicts, error and empty states; Debug builds open the states from Profile › Design states).
- `Core/Offline`: device id, server clock, offline queue, downloads, sync engine and API, `OfflineWork`.
- `Networking`: `APIClient`, `Endpoint`, `APIError`, auth endpoints.

## Languages

- The app offers the 23 languages of the web (`Core/Localization/AppLanguage.swift`), chosen in Profile › Language or from the globe on the sign-in screen; it switches at once, without a restart.
- The language follows the user's Aiku account, as on Android: `GET mobile/profile` sends `language` (`{code, name}` or null) and `LanguageStore.applyAccountLanguage` takes it after sign in, on each profile load and on every return to the app. A choice made in the app is applied at once, kept as `pendingID` (saved on the device) and sent with `PATCH mobile/profile/language`; while it is pending the account language never overwrites it, offline it is sent again later, a 422 drops it and reapplies the account language, and sign out forgets it. Before the first sign in the phone's language is used when supported.
- Every API request sends the app language as `Accept-Language`, so texts the server builds (states, validation errors) come back in the same language.
- Translations live in `Aiku/Resources/Localizable.xcstrings`, keyed by the English text like the web's `lang/*.json`. Shared components (`Core/UI`, Shell rows) look their texts up with `L10n.text(_:)`, falling back to the English text, so texts from the server pass through unchanged; `Text("literal")` follows the root `\.locale`. Values, codes and names are never translated.
- Wording already on the web is reused from `lang/<code>.json`; the rest is machine-translated and marked `needs_review` in the catalogue for a native speaker. Interpolated texts (with `\(...)`) are not translated yet.

## Scanning

- A Bluetooth or built-in scanner works as a hardware keyboard: it types the code and Enter. `.hardwareScanner { code in }` captures that on a screen without a text field or on-screen keyboard. It is on the Scan tab, scan to pick, scan to pack, picking sessions and the barcode camera screens, and is off when Profile › Scanning is set to Camera.

## Design

- The screens follow the "Aiku Mobile" design canvas; its Components page is the reference for shared pieces.
- Reuse the components in `Core/UI` before building a new one: sheets use `.aikuSheet` with `SheetScaffold`, hard-to-undo actions use `.aikuConfirm`, feedback after an action uses `ToastCenter`, problems inside a page use `InlineAlert`, loading uses skeletons.
- Colours come only from `AikuColor` (or `Tone`), so every theme and dark mode work. Colour that carries meaning keeps its own: green for done, red for failed or destructive, amber for blocked or waiting.
- Light, dark and system mode are chosen in Profile › Appearance.
- Touch targets are at least 44 pt; icon-only buttons get an `accessibilityLabel`.

## Verification

All of these must pass before a change is finished:

1. `xcodegen generate`
2. `xcodebuild build -project Aiku.xcodeproj -scheme Aiku -destination 'platform=iOS Simulator,name=iPhone 16'`
3. `xcodebuild test -project Aiku.xcodeproj -scheme Aiku -destination 'platform=iOS Simulator,name=iPhone 16' -only-testing:AikuTests`

Check visible changes on the simulator as well.
