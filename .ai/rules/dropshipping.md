# Dropshipping

## Bundles: derive the whole from the parts, every time

A bundle is one `Product` (`is_bundle`) whose trade units stand in for all of its components.
Everything downstream — available quantity, gross weight, the SKU on the platform variant,
picking — is read off those trade units, so a component missing there is a component missing
from the customer's order. Three ways it goes wrong, all seen in the wild:

- Two components made of the same trade unit. `SyncProductTradeUnits` assigns per trade unit
  (`$tradeUnits[$id] = ...`), so a list carrying the same id twice keeps the last and silently
  drops the rest. Callers must hand it ONE row per trade unit with the quantities already
  added up — it will not do that for you, and this is true of every caller, not just bundles.
- A component that is itself several trade units. The bundle holds
  `component_pivot_quantity * bundle_quantity` of it, not `bundle_quantity`.
- Recomputing from whatever the request happened to mention. After items are created,
  requantified or deleted, read the trade units back off the bundle's CURRENT items
  (`UpdateBundle::getCurrentBundleTradeUnits`). Merging per-branch partials leaves the
  product describing an older component set.

Portfolio `sku` is a snapshot taken at `StorePortfolio` time. Anything that changes a
bundle's components must recompute it via `WithPortfolioSKU::getSKU`, or the platform keeps
selling the old component set. Use `App\Actions\Dropshipping\Bundle\WithBundleTradeUnits`
rather than re-deriving this mapping.

## Platform listed-product payloads share one shape

Every `Get*ListedProducts` / `Search*Products` action feeding the "match to an existing
product" picker must return `id`, `name`, `slug`, `code`, `images` (and `sku_list` where the
platform has variants). The pickers render `item.name` / `item.code` and fall back to the
literal strings "no name" / "no code" — a platform that returns its own vocabulary
(Shopify's `title` / `handle`) renders an entire list of blanks.

## An action returning `[bool, string]` has a result you must check

The Shopify product/variant actions report failure by return value, not by throwing. Calling
one and discarding what it returns turns a rejected push into a 2xx and a "synchronised"
toast, which is indistinguishable to the user from the feature not existing. Propagate it —
`ValidationException` for a retina request — or state in the caller why swallowing is right.

## Shopify: bulk Edit Price sends the price only
Retina bulk Edit Price → Save & Publish (`UpdateAndUploadRetinaBulkPortfolioPriceToCurrentChannel` → `UpdateAndUploadRetinaPortfolioToCurrentChannel::handle` → `updateShopifyChannel`) sends `UpdateShopifyProductVariant`: `price` and `compareAtPrice` (`price` alone for an adopted, matched variant; nothing at all for an adopted variant whose price the merchant manages). `UpdateShopifyProduct` runs only for a portfolio already in Shopify and sends only the text whose words differ from what the edit dialog showed (`changedTexts`: the stored text, or our product's name/description where the portfolio has none, as `DropshippingPortfoliosResource` shows it; `readableText` ignores tags, entities and spacing because the dialog always posts both texts back reformatted), so a price edit or a title edit never rewrites a description the merchant changed in Shopify. A formatting-only change (bold, links, lists, same words) is accepted as not a change and is not sent. The bulk path never sets either text. Never go back to `wasChanged()` there: `UpdateShopifyProductVariant` saves the portfolio again first, so title edits silently never reached Shopify until INI-482. Other platforms differ: the same `handle` calls `UpdateEbayOffer` with `withTitle: true` on eBay, and `UpdateWooProduct` / `UpdateWixProduct` on WooCommerce / Wix. Keep `resources/markdown/dropshipping/docs/product-descriptions-after-connecting*.md` in line with this.

## Bulk Unlink & Delete ends the listing on the platform
The Retina `bulk.unlink` route (`UnlinkAndDeleteBulkRetinaPortfolio`) runs `DeletePortfolio` for each portfolio (queued above `SYNC_LIMIT`). Since HELP-3409 it no longer unlinks first, so `platform_product_id` is still set and `DeletePortfolio` acts on the platform: WooCommerce force-deletes the product, Magento, Wix and Amazon delete it, eBay withdraws the offer, Shopify deactivates the inventory at the aiku- location (`DeactivateShopifyProduct`, the product stays). UI copy and guides must not say the listing stays. `bulk.unlink_only` (`BulkUnlinkRetinaPortfolio` → `UnlinkRetinaPortfolio`) is the one that keeps the platform listing and only clears the link. A bundle's portfolio (`is_bundle`, `bundle_id`) is created only by `StoreBundle`, one per bundle, and nothing rebuilds it, so `DeletePortfolio` runs `DeleteBundle` for it (PRE-10): a bundle never outlives its portfolio. The bulk dialog in `Retina/Dropshipping/Portfolios.vue` and `removing-products*.md` say per platform what happens to the listing.

## eBay: never send a description to a customer's listing
Nobody authorised us to change descriptions in customers' eBay shops (PRE-27, Raul). `UpdateEbayOffer::pushPriceAndTitle` never PUTs the offer: the price goes alone through `bulk_update_price_quantity`, which also works on offers eBay holds without a `listingDescription` (the full `PUT offer` refuses those with 25016), and a Retina title save only changes `product.title` on the inventory item (`updateInventoryItemTitle`). Never add a description fallback, not our snapshot and not the product name. `StoreEbayProduct` still writes a description, both when it creates a listing and when it re-uploads onto an offer that already exists, possibly PUBLISHED (after `bulk.unlink_only`): that is a customer-triggered upload, but nothing else may write one.

## Shopify: a fulfilment order notification can arrive before the request is readable
Shopify can send `fulfillment_order_notification` up to a second before `assignedFulfillmentOrders` lists the request (PRE-34: notified at 10:02:54, `sentAt` 10:02:55Z). The read the webhook triggers then finds nothing, and the order shipped. One immediate read is not enough: the webhook queues `RetrieveShopifyCancelledOrders` again after `RETRY_SECONDS`, and `shopify:sweep-cancellation-requests` runs every 30 min. `CancelOrder` has no guard and refunds every time it runs, so cancellation answers are serialised per store with a lock, and the order state is read only after the lock is taken. To tell the two notification kinds apart in NightOwl, `nightowl_requests_v2.headers_z` is raw deflate (zlib wbits=-15): content-length 30 = FULFILLMENT_REQUEST, 31 = CANCELLATION_REQUEST.

## Channel orders to a banned delivery country: Shopify declines, the rest hold
The shop's banned list is `shops.banned_country_regions` (or the organisation's when `settings.banned_countries.is_follow_organisation_banned_list`), read through `WithOrderForbiddenCountryCheck`. The legacy `forbidden_dispatch_countries` column is read by nothing; `repair:shop_forbidden_countries --shop_id=` copies it across (never run it without `--shop_id`: it overwrites every shop's current list). Shopify: `SplitShopifyFulfillmentRequest` rejects the whole request (never split) and stores a cancelled placeholder; we never cancel the order in the merchant's store. Every other importer goes through `WithPayAndSubmitOrder`: submitted unpaid, with `public_notes` "On hold: ..." (audited, so it shows in the history), and the on-hold email states the reason instead of asking for a card. Both paths record `orders.data.banned_delivery` (country_code, postal_code, by_postcode, reason, at, and platform_rejected for Shopify), which the orders list "Delivery → Banned country" filter reads. The stored `reason` is English; the email rebuilds it with `bannedDeliveryReason()` in the shop's language (HELP-4392).

## A listed or ordered bundle's components never change: duplicate it
Once a bundle's portfolio has `platform_product_id`/`platform_product_variant_id`, or its product is on a submitted order (a basket line, state `creating`, does not count), `UpdateBundle` refuses a different component set (`componentsAreLocked`, ValidationException on `products`); name, description, images and RRP still change. The customer uses `DuplicateBundle` (Retina `bundles.duplicate`): a new product, SKU and unlinked portfolio, published with Create new product, and the old one is ended with Unlink Bundle (`DeleteBundle`). This is why we never push a changed SKU or cost to a Shopify variant (PRE-49): a listed bundle's SKU cannot change from the customer side. `SyncBundlesOfComponent` (our component changed) is aiku's change and still rewrites trade units, leaving a linked sku alone. The edit modal always sends the full `products` list, so the check compares sets, never rejects on presence.

## TikTok: every call is signed for the chosen shop
A TikTok account can hold several shops (one per EU region), and `data.authorized_shop` comes back in a different order on each read. `WithTiktokApiServices::restApi` signs with `tiktok_shop_chiper` (the shop the customer chose), falling back to `authorized_shop.0.cipher` only before a shop is chosen. Warehouses are per shop. `SaveShopDataTiktokChannel` replaces `tiktok_warehouse_id` with the shop's default whenever the stored id is not in that shop's list, so reconnecting with Auth Store (or `tiktok:data_update <slug>`) repairs it (PRE-69). Never sign with `authorized_shop.0` once a shop is chosen.

## TikTok orders shipped by TikTok are always cancelled; keep the shipping note
HELP-4568 (9 Nov 2026). Orders with tiktok shipping_type=TIKTOK arrive with a masked address. Customer service cancels every one: AW ships only with its own couriers, never on TikTok/drop-off labels. StoreTiktokOrder writes "We're unable to ship this order..." into shipping_notes; the warehouse relies on that blue note to stop picking. Never replace it, move it to internal_notes, or add a "do not cancel" alert: HELP-4567 did that (a0ea5644c0) and orders reached picked before it was reverted. Packing one would run ProcessTiktokOrderShipment and request a TikTok label. They are submitted but never charged: WithPayAndSubmitOrder skips PayOrderAsync and the on-hold notice for is_shipping_by_external orders, and RemindChannelOrdersOnHold leaves them out, so they never reach the warehouse and the seller is never asked to pay (PRE-106). They are not auto-cancelled because CancelOrder rejects the order on TikTok.

## eBay drafts: we write to them only when the policy or the seller says so
An eBay draft (data.is_platform_draft, platform_status false) is invisible in Seller Hub (PRE-86). UpdateEbayOffer::handle treats it like a live listing: a reprice reaches it when StoreEbayProduct::sendsOurPrice allows, and a price the seller typed in Edit Product (withPrice) reaches it even under Do not follow RRP. Save as Draft on a draft row updates the eBay draft; Save & Publish updates it, then publishes it (not if eBay refused the update). When eBay refuses the update, UpdateAndUploadRetinaPortfolioToCurrentChannel puts the portfolio back as it was and shows eBay's reason, so My Products never shows a price the eBay listing does not have. PublishRetinaEbayPortfolio and Publish all never push a price or title: a draft can be a seller's own offer (MatchPortfolioToCurrentEbayProduct) or a re-upload onto a PUBLISHED offer, and group (multi-variation) SKUs refuse title writes.

## Shopify orders with a TikTok-hidden address get the do-not-send shipping note
PRE-96 (12 Nov 2026). TikTok orders shipped by TikTok also reach us through the seller's Shopify store, with the address masked ("12****", "DE** ****"). StoreOrderFromShopify::getShippingNotes puts "TikTok hid the delivery address... Do not send it until the full delivery address is on the order." in shipping_notes, ahead of the merchant messages, whenever address_line_1 or postal_code contains "**". Do not cancel or hold these automatically: 4 of the 6 seen in Aug-Nov 2026 were given the real address by staff and then dispatched with our couriers. A masked phone alone is common and is not the signal. The TikTok "We're unable to ship..." merchant message stays filtered out (HELP-4341).

## A portfolio added before its product had an SKO has no sku until one is set
PRE-97 (12 Nov 2026). StorePortfolio stores sku = getSKU, which is null for a non-bundle product with no SKO (often coming-soon). SyncProductOrgStocksFromTradeUnits fills the sku of that product's portfolios whose sku is still null, and never overwrites one that is set (a linked sku must not change, PRE-49). StoreShopifyProduct (first upload) and Store/UpdateShopifyProductVariant call WithPortfolioErrorResponse::portfolioHasSkuOrRecordWhyNot: it recomputes a missing sku, or stores NO_SKU_MESSAGE in errors_response so the customer sees why the match or upload was refused. Rows left empty before this fix get their sku on the next match or upload; no bulk repair was run.

## WooCommerce: a moved store changes address only through reconnect
PRE-109 (16 Nov 2026). A Woo store that moved domain keeps its channel. Retina reconnect takes an optional `url`, and ReAuthorizeRetinaWooCommerceUser puts it in the auth token, sends the customer to that address and refuses one another channel of the customer already uses. CallbackRetinaWooCommerceUser::handleReAuthorization writes `store_url` only once that store sends keys, and drops `settings.webhooks` so CheckWooChannel registers them again on the new store. Never connect the new domain as a fresh store: StoreWooCommerceUser::reconnectExistingStore matches by exact URL and would create an empty second channel. The retina resource reads `store_url` from the column; `settings.credentials.store_url` is legacy.

## eBay: a channel postage policy change moves only the listings on the policy it left
PRE-112 (16 Nov 2026). An eBay offer keeps the postage policy it was published with. When UpdateEbayCustomerSalesChannel changes ebay_users.fulfillment_policy_id (Shipping tab save or picker link), it queues MoveEbayOfferToChannelPostagePolicy per portfolio with an offer. updateOffer(fulfillment_policy_from) PUTs only offers still on the previous policy and only swaps fulfillmentPolicyId: payment, return, location and description stay as eBay holds them. Offers the seller put on another policy are never touched. Never use use_channel_policies here. Refusals (eBay refuses offers held without a description, 25016) are logged, never patched with a description. Repair one channel: `ebay:move-offers-to-channel-postage {channel slug} {old policy id}` runs synchronously and prints moved, skipped and each refusal. Other writers of fulfillment_policy_id (CheckEbayChannel, StoreEbayProduct swap, UpdateEbayUserData, RepairEbayPolicies, ReconnectEbayChannel) do not move listings.

## Shopify: "Use my own shipping rates" turns AW Standard off, never removes the profile
CUS-1834 (16 Nov 2026). The channel setting settings.shopify.own_shipping_rates (toggle in channel Settings > Shipping, saved through UpdateCustomerSalesChannel, which dispatches SyncShopifyDeliveryProfile on change) makes the sync write every AW Standard rate inactive (zonesForRates). The profile stays: under market-driven shipping our variants must ship from aiku-, and only the merchant can add aiku- to "Ships from" on their own market rates, since apps can not write merchant profiles. The flag is in the rates fingerprint and remembered as delivery_profile.own_shipping_rates; when it goes back off, every zone is turned on again (we turned them off, not the merchant), otherwise PRE-82 turned-off zones are kept. Billing is unchanged: orders are still priced by our schema.

## TikTok bulk upload: one job per product, the listing limit stops the run
INI-287 (17 Nov 2026). CreateNewBulkPortfoliosToTiktok only queues StoreNewProductToCurrentTiktok per portfolio not yet on TikTok (tiktok queue), like Shopify. Never upload a whole catalogue inside one job: each product takes several TikTok calls, 618 products outlived the 1 h timeout and the 10 retries re-sent everything for 10 hours. When TikTok answers "Cannot list more products" (shop probation tier, 200 listings), the remaining jobs of that bulk run (cache_key + '_listing_limit') skip the API and store TikTok's message on the portfolio. package_weight is gross ?: marketing ?: 100 g, since TikTok refuses 0.

## eBay: a 25001 on a reused unpublished offer gets one retry on a fresh offer
CUS-1839 (18 Nov 2026). After an eBay "Database Server exception" mid upload, the SKU's unpublished offer answered every updateOffer/publish with errorId 25001 "A system error has occurred. Internal server error", and StoreEbayProduct reused it on every re-upload. StoreEbayProduct::retryOnFreshOffer now deletes that offer (DELETE offer/{id}) and runs handle once more (isRetryOnFreshOffer), only when the offer is not PUBLISHED and our price may replace its price (sendsOurPrice, or no price on eBay), so a live listing or a seller-priced draft is never deleted. Not covered: a 25001 on the inventory_item PUT or on getOffers.

## A bundle's RRP is its portfolio price, and an edit sends it to the platform
PRE-124 (20 Nov 2026). `UpdateBundle` writes the RRP (sent or recalculated from the components) to the portfolio's customer_price and selling_price, then calls `UpdateAndUploadRetinaPortfolioToCurrentChannel` with `customer_price`, so eBay gets `withPrice`. Calling it with `[]` updates only the title: the listing keeps selling at the old price. Bundle portfolios are not in My Products, so this edit is the customer's only way to reprice a bundle.

## Channel language: one gate, new portfolios only, re-translate only on the customer's press
INI-482 (20 Nov 2026). customer_sales_channels.language_id (null = shop language) counts only while the shop's settings.channel_languages switch is on (Shop::customersChooseChannelLanguage, shop settings > Languages, dropshipping shops). The languages offered are CustomerSalesChannel::offeredLanguageIds(): the shop's enabled languages, plus its preview languages for staff customers (INI-510, so staff test a language before customers get it); the settings field shows only when there are two or more. Every reader goes through CustomerSalesChannel::productTextsLocale() (null = today's behaviour) and productText($product, field) (name/description/description_extra from *_i8n, per-field fallback to plain). StorePortfolio snapshots the translated texts; Shopify create sends the portfolio title/description only when the locale is set and the product's own name/description otherwise (unchanged while off). Existing portfolios are never refreshed: only RetranslateRetinaPortfolios (Retina My Products > Re-translate, max UnlinkAndDeleteBulkRetinaPortfolio::SYNC_LIMIT (20), confirmed by the customer) rewrites them, only with texts we have a translation for (never blanking one), keeping platform_handle of a live listing, and sends only the changed texts and never a price: Shopify UpdateShopifyProduct(withTitle, withDescription), WooCommerce UpdateWooProduct(onlyFields), eBay UpdateEbayOffer(titleOnly) without publishing a draft; Wix, TikTok, Magento, Allegro and adopted Shopify variants change in My Products only. A refusal puts the portfolio's texts back, and the result counts in_store / only_my_products / refused honestly. Translation keys in *_i8n are languages.code (checked 20 Nov 2026: every key matches; region codes en-gb/en-au/es-py belong to inactive languages). Never add a bulk refresh, backfill or command for portfolio texts. Amazon listings use Amazon's own catalogue text by EAN, nothing of ours is sent.

## Shopify: an UNSUBMITTED fulfilment order is the merchant's to request, never ours to take
PRE-130 (21 Nov 2026). Shopify sends fulfillment_order_notification only when the store submits the request to our location; a store without automatic fulfilment requests leaves orders UNSUBMITTED for days. buildFulfilmentOrderPayloads imports only SUBMITTED/ACCEPTED, and that stays: never import or accept an UNSUBMITTED request. FetchShopifyOrdersFromApi collects their order names in ordersAwaitingFulfilmentRequest and Retina Fetch orders shows them as a warning asking the customer to press Request fulfillment in Shopify (shopify-order-status*.md says the same). To prove whether a webhook arrived, read the order's audits (url /webhooks/shopify/{id}/fulfillment_order_notification): NightOwl request rows are sampled and miss them.

## WooCommerce description goes out with its document links and as the short description
INI-511 (23 Nov 2026). A Woo product is created with description = short_description = customer_description + '<br><br>' + links to the product's public documents (SDS, IFRA, CPSR...). Every later write of the description must send the same shape, built by StoreWooCommerceProduct::descriptionWithAttachments(): UpdateWooProduct (Edit Product, price edits, Re-translate with onlyFields ['description']) sends both description and short_description from it. Sending the bare customer_description dropped the document links and left the short description in the old language after a Re-translate.

## New channel language: picked on the create page, kept in the session
HELP-4884 (24 Nov 2026). StoreCustomerSalesChannel::customerLanguageId() gives a new channel, while the shop's channel_languages switch is on: the language picked on the Retina create channel page (session retina_new_channel_language_id, set by SetRetinaNewChannelLanguage), else the ?locale the customer opened /app with (session retina_address_locale), else the main web user's language, each only if offered. The pick is kept in the session and also in the cache against the customer (StoreCustomerSalesChannel::rememberNewChannelLanguage, session lifetime), read in that order, so every platform's create flow picks it up without each passing it. The session alone is not enough: the TikTok (webhooks.tiktok.callback), Allegro (allegro.callback) and Wix (wix.link) OAuth callbacks create the channel on the aiku domain, where the customer's retina session cookie is not sent; only eBay, Woo, Shopify, Magento, Amazon and manual create it inside a retina request. Without a pick, those callbacks fall back to the web user's language, not the ?locale the page showed. The picker shows only when two or more languages are offered.

## eBay: a location key is per eBay account, check it on every authorisation
PRE-137 (24 Nov 2026). An ebay_users row re-authorised with another eBay account, or a row that takes over a channel (ReconnectEbayChannel keeps the stale location_key), carries a key that may exist only on the first account. CallbackRetinaEbayUser runs UpdateEbayUserData::restoreLocation after ReconnectEbayChannel, so the key is created (or enabled) on the account just authorised. eBay checks the location at offer create/update, not only at publish: StoreEbayProduct::withLocationRestored retries storeOffer/updateOffer once after restoreLocation, which also covers draft uploads. Do not add this check to CheckEbayChannel: ebay:check sweeps every channel, and that would be a bulk repair.

## TikTok: a category that requires certifications is refused before the create
PRE-140 (26 Nov 2026). Our upload cannot carry certification files, and TikTok rejects a create whose required certifications have none. StoreProductToTiktok first tries resolveSafeCategoryId; if the final category still requires certifications it throws CERTIFICATIONS_REQUIRED_MESSAGE (the portfolio gets it as errors_response, the log FAIL) and never POSTs. The customer's path is to create the product in Seller Center with its documents and match it in My Products; connecting-tiktok-shop*.md quotes the message's bold opening, so change both together. Never send required certification ids with 'files' => [].

## TikTok fulfilment orders packed outside aiku follow TikTok's status, per channel switch
HELP-4974 (27 Nov 2026). Tough Glove's TikTok orders (fulfilment, shipping_type TIKTOK) are packed at Europa Drive outside aiku, so their pallet returns sat confirmed forever (1,355 cancelled 27 Nov). SyncTiktokFulfilmentOrderStatus, run from HandleOrderIncomingTiktok and daily by tiktok:sync-fulfilment-orders, follows TikTok only on channels with customer_sales_channels.settings.sync_fulfilment_orders_from_platform = true: IN_TRANSIT/DELIVERED/COMPLETED picks each line from its allocated pallet (capped at what aiku has, the shortfall written to internal_notes), sets picked and dispatches; CANCELLED cancels. Dispatch only when is_shipping_by_external, so FulfillOrderToTiktok never sends tracking. Same per-order lock as ValidateIncomingTiktokOrder. Switch it on by merging the key into settings, never by replacing the array. The charge per parcel is not built yet (Tough Glove's PICK PER ITEM is 100% off); it waits on the price James picks.
