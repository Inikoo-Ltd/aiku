# Actions Procurement

## Agent warehouse: read what is held through AgentWarehouseStock::heldQuantitySql, never quantity
INI-206 (5 Nov 2026). Nothing writes agent_warehouse_stocks when goods go in a container or the container is dispatched, so a row's quantity is what was received, not what the agent still holds. Held = quantity minus the units of the same purchase_order_transaction_id on live stock delivery items (any state but cancelled/not_received, staged or dispatched), taken from the line's packed rows first, then its oldest, so a later goods receipt for the rest of a line stays held and an unpacked lot is not hidden by a packed one that shipped. PO stages keep reading the raw quantity for the packed date. Every reader of "what the agent holds" (Warehouse screens, backlog, ready checks, stages, packable quantities) uses AgentWarehouseStock::heldQuantitySql() / whereHeld() / heldQuantityColumn(). Do not add a write path that decrements rows on dispatch: undispatch, cancel and item edits would all need to restore it.

## Ordering suggestions skip seasonal SKOs that would arrive out of season
HELP-4598 (10 Nov 2026). A product-property tag can carry a season (tags.arrive_from_month / arrive_to_month, 1-12, may wrap the year end; set on the tag edit page): the months its goods should arrive in. Tag::outOfOrderingSeasonSql($stockIdColumn, $leadDays) is true for a stock whose trade units or their families carry seasonal tags, when today plus the lead time lands outside all of them, so a slow agent opens months before a fast partner on the same tag. Every query that proposes what to order applies it next to is_excluded_from_auto_ordering with that path's own lead time: SuggestPartnerShoppingList::candidates and GetPartnerStockCoverBuckets::rescuableQuery (GetPartnerLeadTime; reason out_of_season in leftOut), SuggestAgentShoppingList (GetAgentStockCoverBuckets::leadTimeExpression), SuggestSupplierShoppingList (the SKO's, the supplier product's, then the supplier median); HubOrderPlanningTool reports out_of_ordering_season. A new suggestion path must apply it too. Adding by hand, bucket counts and the recommended-quantity chips are deliberately not gated.

## A purchase order's progress is purchase_orders.state only: never compare with CONFIRMED
INI-244 (12 Nov 2026). purchase_orders.state holds the whole path: in_process, submitted, confirmed (Agreed), in_production, in_warehouse, ready, handed_over, arrived, settled, plus cancelled and not_received. There is no stage column and no bucket SQL. People draft, submit, agree, cancel; goods-in settles (syncSettlement); between confirmed and arrived PurchaseOrderHydrateState moves the state to the furthest stage GetPurchaseOrderStages reports, forward and back, and refreshes the per-state counters. A submitted order stays submitted until agreed. Never write `state === CONFIRMED` or `in ('submitted','confirmed')`: use PurchaseOrderStateEnum::open() / agreed() / live() (…Values(), …Sql(), isOpen(), isAgreed(), isLive()). Lines stop at confirmed: copy an order state onto a line with ->transactionState(). A fetch or repair that sets state confirmed on an order already past it is ignored (UpdatePurchaseOrder::keepsStateReached). A select alias named `state` or `stage` next to GROUP BY groups by the table column in Postgres, not the alias. purchase_orders.delivery_state stays: it is the containers' state, a resolver input with its own counters.

## A purchase order's total is its items; extras live on the stock delivery
INI-237 (Raul, 12 Nov 2026). purchase_orders.cost_total always equals cost_items: CalculatePurchaseOrderTotalAmounts::itemsNet is the one place the items are added up, and PurchaseOrderHydrateTransactions stores that same figure, only when it differs (INI-247: it used to store the plain sum of the lines, overwriting the converted one). A line keeps the currency its amount is in (purchase_order_transactions.currency_id, INI-247): WithStoreProcurementOrderItem sets it from the supplier product for a line made in aiku, the Aurora fetch passes the order's, a moved line takes its source line's, a line with no supplier product is in the order's. Totals convert by the line's currency at the order date. Never read a line's currency from its supplier product (it changes: GBot-26 went from CNY to GBP and a 2,400 CNY line would have become about 21,858) or from its exchange rate (same-currency lines carry other rates, Aurora lines carry 1.0). Any new path that writes a line's net_amount in a currency other than its supplier product's must pass currency_id. cost_extra, cost_shipping, cost_duties and cost_tax on purchase_orders are dead columns: nothing reads, shows, accepts or restores them (PO page, export, journey, Aurora fetch, UpdatePurchaseOrder, cancel and undo cancel). Freight, duty, agent and other landed costs are entered and seen on the stock delivery only, and agents never see them. Do not add a reader or writer of these columns. repair:purchase_order_costs (dry run unless --apply) cleared the old values and kept them in purchase_orders.data.costs_before_extras_cleared. Unit expenses (agent_unit_expense on lines, unit_expense on supplier products) are a separate estimate and never part of cost_items or cost_total.

## A deposit payment's amount is always in the order's currency; what was sent is original_amount
HELP-4668 (12 Nov 2026). purchase_order_deposit_payments.amount and currency_id are always the purchase order's: every reader sums amount without looking at a currency (SyncPurchaseOrderDepositPaid paidAmount/leftToPay, ShowPurchaseOrder::getPayments, ShowStockDelivery::getSupplierPayments). Money sent in another currency (the organisation's, US dollars or euros, ConfirmPurchaseOrderPayment::paymentCurrencies) is kept beside it in original_amount / original_currency_id, as agent_payments does. The person recording the payment types what it counts for on the order; the server never converts it, because a converted figure would overshoot or leave a few units of what is left to pay. original_* is a record only: never sum it, never feed it into costing, exchange rates or order totals.

## Pulling items into a PO moves only what the agent has not received
Vika, 13 Nov 2026. "Add from another PO" (PullPurchaseOrderTransactions) is MovePurchaseOrderTransactionToSupplier::handle with $into: the target is any live agent order (canPullInto), the source any open order of the same agent and currency (purchaseOrdersToPullFromQuery), of the same supplier or another one. Unlike a push move it is allowed after production started or a deposit was paid (the dialog warns), so it cancels the source line with CancelPurchaseOrderTransaction evenInProduction. That is safe only because pullableQuantities caps each line at quantity_ordered minus the units in agent_warehouse_stocks and blocks lines on a live stock delivery: never lift that cap. A buyer pulling from another supplier takes that supplier's price (acceptsSupplierPrice); an agent pulling keeps the agreed price and asks the buyer.

## A draft PO follows the organisation's delivery address; submit copies it
Vika, 13 Nov 2026. purchase_orders.data.delivery_address on a draft (in_process) is only an address typed for that one order; empty means it follows ResolvePurchaseOrderDeliveryAddress (procurement setting, then first warehouse). StorePurchaseOrder copies the default only for an order stored past draft; UpdatePurchaseOrderStateToSubmitted copies it at submit, so a sent order keeps the address the supplier got. Emptying the address on a submitted order (UpdatePurchaseOrder::deliveryAddress) takes the organisation's current one, never null. Drafts created before this carried a copy: repair:draft_purchase_order_delivery_addresses (dry run unless --apply) clears copies that equal the organisation's own addresses. The PO page edits it through the pencil in ProcurementOrderData (buyer with procurement edit, until handed over).
