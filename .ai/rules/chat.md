# Chat

## AI coverage: one outcome per customer message
chat_ai_outcomes holds one row per (session, trigger_message_id), enforced by partial unique indexes; write it only through StoreChatAiOutcome, which keeps the stronger outcome by ChatAiOutcomeEnum case order (draft first). GetChatAiCoverage counts each chat once, by the customer's latest message in the window: the recorded outcome, else a staff reply after it, else is_spam, else is_rubbish (as notice), else not worked. A newer customer message is new work, so an outcome on an earlier one no longer covers the chat. Team windows (today/overnight/team hours) come from config('chat.ai_teams').

## Verified chat facts: two chats to trust, staff removal sticks
Shop facts the CS assistant's reviewers check live in chat_knowledge_entries with source_type verified, written only through RememberVerifiedChatFact (MCP remember_fact). A fact is a candidate until checked while working two different chats, then active for TRUSTED_DAYS; a fact repeating the customer's own words is refused, so one planted message cannot become a rule. Rating a draft wrong_fact disputes the facts in its facts_used; discarding one disputes them only when the agent's next reply says something else (SettleChatAiDraft::settleDiscarded, under REWORDED words kept), because staff discard to clear the box and then type the same answer (INI-400: 230 of 388 discards were followed by a reply within 10 minutes); staff Remove on /chat/ai/verified-facts is final for the tool. HydrateChatKnowledge must never delete verified rows (it only prunes webpage, shop_settings, docs).

## One WhatsApp thread per contact per shop: three lookups stay in step
StoreIncomingWhatsappMessage::findSession, HandleWhatsappCallEvent::resolveSession and StoreMetaChatSession find a contact's thread the same way: withTrashed, never one whose metadata->merged_into is set (MergeMetaChatSessions::MERGED_INTO_KEY), live first, and a binned thread is restored rather than a second one started beside it (that is how prod got its only same-shop duplicates). Each shop writes from its own WhatsApp number and keeps its own customers, so the same phone in two shops is two real conversations: never merge them, they meet in the conversation history (GetCustomerChatHistory::forConversation) instead.

## Draft status stays as staff see it; change_class is the measure
SettleChatAiDraft::statusFor and its thresholds (used/edited/superseded) feed the adoption stats, coverage and the draft-box counts: never retune them to answer a new question. How much staff changed a draft lives in chat_ai_drafts.change_class (MeasureChatAiDraft: as_is, cosmetic, gaps_filled, small, big, rewritten, own_reply, discarded), with words_kept, lag_seconds and open_to_reply_seconds. A draft whose [[gaps]] staff filled counts as "used" in status but gaps_filled here, and only as_is/cosmetic could ever go out without a person. open_to_reply_seconds is time from the message being opened to the reply, not time spent working: never divide payroll by it. chat:measure-drafts runs nightly and is also the backfill.

## Claim outcomes are an estimate by order and timing, one case per chat and order
chat_ai_drafts.claim_check (MeasureChatAiClaim, chat:measure-claims nightly, also the backfill) labels damaged/missing/wrong item drafts by what was done on the order within 7 days: refund invoice, compensation/add_funds_other credit (never pay_return, which every refund-to-balance writes too), replacement delivery note, follow-on in the next order. Values are net in the group currency so bands (config chat.claim_value_bands) compare across shops. Never value a proposal with PlanChatClaim after the fact: once settled it sees nothing left to claim. No order found = no_order, kept out of the rates. GetChatAiClaims counts one case per conversation and order, taking its best-matching draft. Jev's reply verdict is the honesty check, since refunds are not linked to chats.

## Chats handed over by the AI shopping assistant stay out of chat figures
INI-245 (12 Nov 2026): a chat the assistant handed over carries chat_sessions.shopping_assistant_conversation_id. GetChatAiCoverage and the default GetChatReports figures (fromAssistant false) exclude it, because it would read as an unanswered chat overnight and as CS-assistant work; the chat reports page shows only those chats with from_assistant=1, and the AI Assistant report counts hand-overs from shopping_assistant_hand_overs. The assistant transcript is read from the assistant's own tables by GetChatAssistantTranscript and never copied into chat_messages, because GetChatReports counts an ai message as the first reply. These chats stay in the normal inbox, unclaimed queue and alerts (WithUnclaimedChatSessions and AlertUnclaimedChatSessions are untouched on purpose).

## Shop facts recommend the right shop, rarely: dropshipping by organisation, customers across the UK/EU border
Raul, 17 Nov 2026: recommend another shop only when it truly helps the customer, never as a habit; customers must not be bounced between shops. GetChatShopFacts adds two kinds of shop facts. (1) Dropshipping: every B2B shop links its organisation's dropship shop (DROPSHIPPING_SHOP_BY_ORGANISATION: aw→awd, sk→dssk, es→dse, aroma→awd), which sells almost everything as single units. (2) "Customers in <country>": only across the UK/EU customs border (customsSide, by the organisation's address country, because shops.country_id is wrong for dssk): the shop of the same master_shop that most customers registered in that country bought from over 12 months, with at least HOME_SHOP_MIN_CUSTOMERS and twice this shop's count, only for countries this shop has customers from. ## Writing to Slack as a person: one client, production only, public channels checked by aiku
Raul, 21 Nov 2026 (INI-452). A person's own Slack user token lives in slack_connections (SlackConnection: token encrypted and hidden, one row per aiku user and Slack workspace since INI-540); the bot token never writes as a person. Every write goes through SlackWriteClient::for($user)->call(), which is null unless SlackWriteAccess::allows (active and may read Slack channels, so any staff member linked to a Slack person; open to all staff since 25 Nov 2026, Raul, not announced), the environment is production or testing (a local machine can hold a copy of production tokens), and the connection is live. token_revoked, invalid_auth, account_inactive and missing_scope set needs_reconnect before SlackWriteException is thrown. Scopes are SlackWriteAccess::USER_SCOPES (chat:write, reactions:write, and since 24 Nov 2026, before anyone had connected, also files:write, channels:write, pins:write, bookmarks:write and reminders:write for the rest of phase 3, so nobody reconnects as those tickets land; a ticket that needs another adds it there and in the Slack app, and every connection whose stored scopes lack it is then asked to reconnect instead of failing on missing_scope). None reads, and Slack does not limit them to public channels, so each write action checks SlackChannel::isVisibleTo on its target channel. A 429 throws ratelimited at once (no sleep in a web worker) and a token that cannot be decrypted flags needs_reconnect. Connect, callback and disconnect are gated on the same WRITE_ENVIRONMENTS: other machines never obtain a token and disconnect only locally. The connect callback accepts only config services.slack.team_id and the Slack person of SlackChannel::linkedSlackPerson (the access policy's link rule), consumes its state once, and revokes a token it refuses to keep. Disconnect and user deactivation call auth.revoke and clear the token; the row stays. Token rotation must stay off in the Slack app: a rotating token is refused. Stand-in (INI-548, Raul 25 Nov 2026): a person allowed to write but not connected posts, edits and deletes through the Desk bot (SlackWriteClient::standInFor, chat:write.customize with their Slack name and photo; Slack shows an APP label), and the composer then offers Connect. The row is stored as the person (slack_user_id, user_id, no bot_message subtype); StoreSlackMessage keeps that author when Slack's echo or edit event arrives with bot_id and no user. Reactions always need the person's own connection. After connecting, earlier stand-in posts cannot be edited with the person's token (Slack answers cant_update_message).

## Verba files over 25 MB go browser to R2, then a job relays them to Slack
Raul, 28 Nov 2026 (INI-491 part 5). UploadSlackFile handles files up to 25 MB, because Octane stops a request at 45 s and Cloudflare at 100 MB. Larger files, up to 1 GB, go through UploadSlackLargeFile, which works in four steps:
1. Start: aiku creates the multipart upload under slack-uploads/{ulid} on staff-chat-r2 and signs one UploadPart link per 50 MB part, valid 2 h. The browser PUTs the parts straight to R2.
2. Complete: aiku checks the real size with HeadObject against the size declared at start. On a mismatch it deletes the object and refuses.
3. Queued job (ids only, one try): sniffs the real type from the first 64 KB, then streams R2 to Slack with the person's own client.
4. The job leaves the cache key UploadSlackFile::cacheKey, so SendSlackFiles completes the send unchanged. A channel file up to the media limit (50 MB) moves into the media library like every other copy; above it the object is moved to slack-files/{file id}/{name} as its slack_files copy, so slack-uploads/ only ever holds work in progress and an R2 lifecycle rule (delete after 1 day) cleans every orphan. The disk has stream_reads on: without it every readStream downloads the whole object first. Start refuses only REFUSED_TYPES (the browser's type is unreliable); the job's sniff is the real check. complete is claimed once with Cache::add. inComplete and inStatus skip authorize() (laravel-actions runs it only for asController), so stateFor's user and channel match is their whole gate. A DM file's object is deleted. On any failure the object is deleted.
The upload state is in the cache, readable only by the uploader in that channel. The bucket needs a CORS rule for the app origin (PUT, ExposeHeaders ETag). R2 drops unfinished multipart uploads itself.
