# Supply Chain

## Units per pack is set in the SKO composition, read org_stocks.packed_in
HELP-4263 (23 Oct 2026). A supplier product's units_per_pack mirrors the SKO trade unit composition: SupplierProduct::skoPackedIn() is the answer, SyncStockTradeUnits pushes it onto linked supplier products, and AttachOrgSupplierProductToOrgStock copies it when a supplier product is first linked to a stock, and UpdateSupplierProduct overrides any other value except from the Aurora fetchers (the only callers passing skipHistoric: true, which keep Aurora's own value). The edit forms show the field read-only. Read packing from org_stocks.packed_in: stocks.packed_in is null for ~21k Aurora stocks. The supplier product's own trade unit pivot quantity is the size of one supplier unit, not the pack: never sync it to the pack. A carton holds a number of SKOs: when the SKO packing changes, SyncStockTradeUnits passes the old packing and SyncSupplierProductUnitsPerPackFromSko rescales units_per_carton so the SKOs per carton stay the same (the upload stores only units_per_sko × skos_per_carton), but only for supplier products whose pack matched the old packing: ~240 Aurora supplier products carry their own package unit, where the ratio means nothing. Draft PO lines keep the historic supplier product they were added with: the packing PDF reads the live supplier product while the order is in process, and submitting re-points the lines to the current historic.

## A supplier's agent fee overrides the client's, per line
Vika, 13 Nov 2026. suppliers.agent_fee_percentage (set by the agent on its supplier edit page, shown only in the agent's own organisation, or from the Agent Ledger client cards, both through UpdateSupplierAgentFeePercentage) is the fee on that supplier's goods; null falls back to the client's org_agents.agent_fee_percentage, then 2 (SyncAgentInvoiceChargesFromLedger::clientFeePercentage). recordAgentFee groups the invoice lines by stock_delivery_item → supplier_product → supplier and adds up each group's fee, so a container with several suppliers gets one fee line with a mixed note. Any new place that works out an agent fee must use the same per-supplier fallback.

## An order that missed CHO takes the client's CHO penalty off its agent fee
Vika, 13 Nov 2026. When the agent invoice is issued, SyncAgentInvoiceChargesFromLedger::goodsByFeePercentage links each line to its PO through stock_delivery_items.data->purchase_order_transaction_id. The goods of a PO that missed clean hand over pay the fee less org_agents.cho_penalty_percentage, in percentage points: the migration filled 1 for every client and it is the column default for new ones, empty or 0 is no penalty, and the fee never goes below 0%. Only the client sets the penalty, on EditOrgAgent through UpdateOrgAgent; the Agent Ledger card only shows it. CHO passes when every Ready to Roll check the agent asks for (balance, packing, QC, from GetPurchaseOrderStages::readyChecks; a skipped check counts as done) is done, with no deadline. Compliance never counts: readyChecks marks it required: false, done (green) only once compliance_complete_at is set and shown skipped until then, as not every item needs it; consumers of readyChecks (automatic hand over, the dispatched-without note, CHO) ignore checks that are not required. The buyer or the agent (compliance_complete_at is in AGENT_MARKABLE_FIELDS) completes it from the check's modal on the PO page: GetAgentCleanHandoverScore::cleanHandoverMisses lists the checks not done and returns null, meaning no penalty, for chs_excluded orders and agents with no checks. The PO page shows the badge only once Handed over is reached. The fee note uses the same method. The quarterly CHS commission tiers are separate and display only.

## The group Suppliers list shows every supplier, free and through agent
Vika, 16 Nov 2026. grp.supply-chain.suppliers.index (IndexSuppliers) lists free and agent suppliers together, filtered by the Type element group (free / through_agent / archived), with Agent and Nickname columns; the global search also matches company_name, contact_name, agents.code and the code of any of the supplier's products. The Agent Suppliers menu entry is gone: links that meant "agent suppliers" go to suppliers.index with elements[type]=through_agent, and "free suppliers" with elements[type]=free. The Purchase Orders cell adds the open count: number_open_purchase_orders + number_purchase_orders_state_in_process (everything not settled, cancelled or not received).

## Archiving a supplier leaves its products alone
Vika, 16 Nov 2026. A supplier is archived when suppliers.status = false and archived_at is set; that is the Archived filter on the supplier lists. DeactivateSupplier (agent change request, or the Archive button on the supplier page through grp.models.supplier.archive) and ReactivateSupplier (grp.models.supplier.unarchive) are the only paths. Both are open to group admins and to the org admins of any organisation with an org supplier for that supplier (DeactivateSupplier::canArchive). Archiving switches off the org suppliers and keeps their ids in suppliers.data.archived_org_supplier_ids, so unarchiving switches back on only those. Neither path touches supplier products, org supplier products or catalogue products: they stay active (decided by Vika).

## suppliers.name holds the nickname when one is set
Vika, 16 Nov 2026. suppliers.name is the nickname when staff set one, otherwise it is filled from company_name (or contact_name). Never show suppliers.name as "Name": use Supplier::officialName() for the real name and Supplier::nickname() for the nickname column. In SQL the official name is coalesce(nullif(company_name, ''), contact_name, name); IndexSuppliers sorts its Name column on that as official_name.

## Material planning notes are supplier submissions and never approve compliance
INI-279 (Vika, 16 Nov 2026). Material notes, reservation dates and sourcing documents that suppliers send from Plan for next orders are supplier_submissions of type material_planning. They need no table of their own: the product line of the plan at the time of sending is kept in data.plan, and data.escalated_for records the sending that was already escalated. Accepting a note changes nothing in aiku. ApplySupplierSubmission has no branch for it, and its documents never touch compliance or supplier attachments. The buyers of the product (purchasingLeads) are told only when a sending carries new data or files. A note with no reply after group settings supplier_portal.planning_escalation.days goes, once per sending, to the user_ids set there (Supplier page settings dialog); an empty list means no escalation.

## INI-277 and INI-278 must finish INI-279's planning notifications
INI-279 (16 Nov 2026) left three planning notifications to the tickets that create their events: "buyer review requested" and "reviewed forecast published" (INI-278), and "volume quote submitted" (INI-277). Each one is a new UserNotificationEnum case in PROCUREMENT_EVENTS, sent through NotifyPurchasingOfSupplierPlanningNote::send() with SupplierPlanningNoteNotification (or a sibling), and sent only when the information changed. Overdue review requests and quotes are added to EscalateOverdueSupplierPlanningNotes, which uses the same planning_escalation days and recipients. A quote also takes material notes and documents, just as a material_planning note does, and approves no compliance. Exports of the plan or of quotes carry the exact wording: "For planning only. This is not a purchase order or authority to buy materials or begin production. Quantities and dates may change."
