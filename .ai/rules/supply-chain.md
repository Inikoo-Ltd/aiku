# Supply Chain

## Units per pack is set in the SKO composition, read org_stocks.packed_in
HELP-4263 (23 Oct 2026). A supplier product's units_per_pack mirrors the SKO trade unit composition: SupplierProduct::skoPackedIn() is the answer, SyncStockTradeUnits pushes it onto linked supplier products, and AttachOrgSupplierProductToOrgStock copies it when a supplier product is first linked to a stock, and UpdateSupplierProduct overrides any other value except from the Aurora fetchers (the only callers passing skipHistoric: true, which keep Aurora's own value). The edit forms show the field read-only. Read packing from org_stocks.packed_in: stocks.packed_in is null for ~21k Aurora stocks. The supplier product's own trade unit pivot quantity is the size of one supplier unit, not the pack: never sync it to the pack. A carton holds a number of SKOs: when the SKO packing changes, SyncStockTradeUnits passes the old packing and SyncSupplierProductUnitsPerPackFromSko rescales units_per_carton so the SKOs per carton stay the same (the upload stores only units_per_sko × skos_per_carton), but only for supplier products whose pack matched the old packing: ~240 Aurora supplier products carry their own package unit, where the ratio means nothing. Draft PO lines keep the historic supplier product they were added with: the packing PDF reads the live supplier product while the order is in process, and submitting re-points the lines to the current historic.

## A supplier's agent fee overrides the client's, per line
Vika, 13 Nov 2026. suppliers.agent_fee_percentage (set by the agent on its supplier edit page, shown only in the agent's own organisation, or from the Agent Ledger client cards, both through UpdateSupplierAgentFeePercentage) is the fee on that supplier's goods; null falls back to the client's org_agents.agent_fee_percentage, then 2 (SyncAgentInvoiceChargesFromLedger::clientFeePercentage). recordAgentFee groups the invoice lines by stock_delivery_item → supplier_product → supplier and adds up each group's fee, so a container with several suppliers gets one fee line with a mixed note. Any new place that works out an agent fee must use the same per-supplier fallback.

## An order that missed CHO takes the client's CHO penalty off its agent fee
Vika, 13 Nov 2026. When the agent invoice is issued, SyncAgentInvoiceChargesFromLedger::goodsByFeePercentage links each line to its PO through stock_delivery_items.data->purchase_order_transaction_id. The goods of a PO that missed clean hand over pay the fee less org_agents.cho_penalty_percentage, in percentage points: the migration filled 1 for every client and it is the column default for new ones, empty or 0 is no penalty, and the fee never goes below 0%. Only the client sets the penalty, on EditOrgAgent through UpdateOrgAgent; the Agent Ledger card only shows it. CHO follows the PO page (GetAgentCleanHandoverScore::cleanHandoverMisses): once the goods are handed over and a CHO date is expected (approved_ready_at, else the journey board plan), only the timing counts, on or before that date passes, later fails, no tolerance; before that, every Ready to Roll check the agent asks for (balance, packing, QC, from GetPurchaseOrderStages::readyChecks; a skipped check counts as done) must be done. purchase_orders.not_received_at is never part of CHO (only Aurora filled it). Compliance never counts: readyChecks marks it required: false, done (green) only once compliance_complete_at is set and shown skipped until then, as not every item needs it; consumers of readyChecks (automatic hand over, the dispatched-without note, CHO) ignore checks that are not required. The buyer or the agent (compliance_complete_at is in AGENT_MARKABLE_FIELDS) completes it from the check's modal on the PO page: GetAgentCleanHandoverScore::cleanHandoverMisses lists the checks not done and returns null, meaning no penalty, for chs_excluded orders and agents with no checks. The PO page shows the badge only once Handed over is reached. The fee note uses the same method. The quarterly CHS score (GetAgentCleanHandoverScore::isCleanHandover) uses the same rule, counting an order clean only once handed over on time (handOverTiming days_late 0); its tiers are display only. The fee follows CHO after the invoice is issued: SyncAgentInvoiceChargesFromLedger::refreshAgentFeeOfPurchaseOrders reworks it while chargesOpen, called by UpdatePurchaseOrder when handed_over_at, approved_ready_at, proposed_ready_at, chs_excluded or not_received_at change, and by RecordPurchaseOrderHandedOverWhenReady while the order is not handed over. A change of the fee or penalty percentage still applies only to invoices issued after it.

## The group Suppliers list shows every supplier, free and through agent
Vika, 16 Nov 2026. grp.supply-chain.suppliers.index (IndexSuppliers) lists free and agent suppliers together, filtered by the Type element group (free / through_agent / archived), with Agent and Nickname columns; the global search also matches company_name, contact_name, agents.code and the code of any of the supplier's products. The Agent Suppliers menu entry is gone: links that meant "agent suppliers" go to suppliers.index with elements[type]=through_agent, and "free suppliers" with elements[type]=free. The Purchase Orders cell adds the open count: number_open_purchase_orders + number_purchase_orders_state_in_process (everything not settled, cancelled or not received).

## Archiving a supplier leaves its products alone
Vika, 16 Nov 2026. A supplier is archived when suppliers.status = false and archived_at is set; that is the Archived filter on the supplier lists. DeactivateSupplier (agent change request, or the Archive button on the supplier page through grp.models.supplier.archive) and ReactivateSupplier (grp.models.supplier.unarchive) are the only paths. Both are open to group admins and to the org admins of any organisation with an org supplier for that supplier (DeactivateSupplier::canArchive). Archiving switches off the org suppliers and keeps their ids in suppliers.data.archived_org_supplier_ids, so unarchiving switches back on only those. Neither path touches supplier products, org supplier products or catalogue products: they stay active (decided by Vika).

## suppliers.name holds the nickname when one is set
Vika, 16 Nov 2026. suppliers.name is the nickname when staff set one, otherwise it is filled from company_name (or contact_name). Never show suppliers.name as "Name": use Supplier::officialName() for the real name and Supplier::nickname() for the nickname column. In SQL the official name is coalesce(nullif(company_name, ''), contact_name, name); IndexSuppliers sorts its Name column on that as official_name.

## Material planning notes are supplier submissions and never approve compliance
INI-279 (Vika, 16 Nov 2026). Material notes, reservation dates and sourcing documents that suppliers send from Plan for next orders are supplier_submissions of type material_planning. They need no table of their own: the product line of the plan at the time of sending is kept in data.plan, and data.escalated_for records the sending that was already escalated. Accepting a note changes nothing in aiku. ApplySupplierSubmission has no branch for it, and its documents never touch compliance or supplier attachments. The buyers of the product (purchasingLeads) are told only when a sending carries new data or files. A note with no reply after group settings supplier_portal.planning_escalation.days goes, once per sending, to the user_ids set there (Supplier page settings dialog); an empty list means no escalation.

## INI-277 and INI-278 must finish INI-279's planning notifications
INI-279 (16 Nov 2026) left three planning notifications to the tickets that create their events: "buyer review requested" and "reviewed forecast published" (INI-278), and "volume quote submitted" (INI-277). Each one is a new UserNotificationEnum case in PROCUREMENT_EVENTS, sent through NotifyPurchasingOfSupplierPlanningNote::send() with SupplierPlanningNoteNotification (or a sibling), and sent only when the information changed. Overdue review requests and quotes are added to EscalateOverdueSupplierPlanningNotes, which uses the same planning_escalation days and recipients. A quote also takes material notes and documents, just as a material_planning note does, and approves no compliance. Exports of the plan or of quotes carry the exact wording: "For planning only. This is not a purchase order or authority to buy materials or begin production. Quantities and dates may change."

## A supplier product follows discontinuing SKOs in the group row only, and only its own change is undone
INI-288 (Raul, 17 Nov 2026). SyncSupplierProductsDiscontinuingFromSkos runs in real time from StockHydrateStateFromOrgStocks on every stock state change and from AttachOrgSupplierProductToOrgStock when a SKO is newly linked, plus the supply-chain:supplier-products-follow-discontinuing-skos command for the backfill (--dry-run gives counts per supplier); it needs no schedule. An active supplier product turns discontinuing when every SKO it supplies is discontinuing or discontinued, with at least one discontinuing. Purchase orders do not hold it back (Raul): nothing operational reads the group state, and an open order carries on through the org rows. Do not add an open-PO exemption: it would need a re-check on every path that ends an order or a line. It goes back to active only when it carries data.discontinuing_from_skos_at (UpdateSupplierProduct::FOLLOWS_DISCONTINUING_SKOS_KEY) and a SKO is no longer retiring. UpdateSupplierProduct with followsSkoStates: true writes that mark and does NOT cascade the state to org_supplier_products: a discontinuing org row would block AddItemNotOnPurchaseOrderToStockDelivery and MovePurchaseOrderTransactionToSupplier. Any other state given, a buyer's or DiscontinueDeadOrgSupplierProducts', clears the mark, so a hand-set state is never undone; a buyer giving the same discontinuing (edit or BulkUpdateSupplierProductsState) takes it over and it reaches the org rows. A marked product a person puts back to active gets data.kept_active_by_hand_at (KEPT_ACTIVE_BY_HAND_KEY) and the sync leaves it active until someone changes its state again. The supplier portal shows discontinuing as discontinued, with no message to the supplier (decided).

## Supplier products are shared between suppliers in both directions through CopySupplierProductsToSupplier
Vika, 18 Nov 2026. On an agent supplier's Supplier Products page the agent can push selected products to another supplier (org_supplier_products ids) or pull products from another supplier (Add products from another supplier dialog, supplier_products ids, listed by GetSupplierProductsToCopy). Both post to grp.models.org.supplier.supplier_products.copy and run CopySupplierProductsToSupplier, which skips codes the target already has and converts money across currencies. Sources and targets are limited to suppliers of agents whose procurement the user may edit (getAccessibleAgents), plus free suppliers on a free supplier's page; do not add another copy action.

## Merging suppliers merges their same-code products first
Vika, 18 Nov 2026. Approving a merge suggestion (DecideSupplierChangeRequest → MergeSuppliers) used to fail whenever both suppliers had products with the same code, which is common for Aurora duplicates (Gloria → GA had 20). MergeSuppliers now runs MergeSupplierProducts::mergeSupplier (dry run in ensureCanMerge, then fix: true inside the same transaction) before moving anything. It refuses only when a shared product cannot be merged (different units per pack, trade units or SKOs), and the error names each code with its reason.

## The discontinued reason lives in supplier_products.data and the supplier sees it
Vika, 18 Nov 2026. Setting a supplier product to discontinuing or discontinued (row Set or bulk Set state on Supplier Products) asks for an optional reason, stored in data.discontinued_reason (UpdateSupplierProduct::DISCONTINUED_REASON_KEY, max 500). It is replaced only when discontinued_reason is passed (empty clears it), so automation moving discontinuing to discontinued keeps it, and it is cleared when the state goes back to active or in process. IndexSupplierPortalProducts sends it as status_reason and the supplier portal shows it as a popover on the Discontinued status (hover or click).

## Add to another supplier can make the target the preferred supplier
Vika, 18 Nov 2026. CopySupplierProductsToSupplier takes make_preferred (checkbox in the Add to another supplier dialog). When set, for every SKO the source product and the target's product both supply, it runs SetStockPreferredSupplierProduct (group priority + local_priority in every organisation), so purchase orders go to the target. It also applies to products the target already had under the same code (not trashed), so the request no longer fails with "already has all" when make_preferred is on. Making preferred re-points SKOs in every buying organisation, so it needs goods.edit (the permission SetStockPreferredSupplierProduct asks for), not only the agent's procurement edit: without it asController/inGroup give a make_preferred validation error and getCopyProductsProps sends can_make_preferred false, which hides the checkbox. Targets that are discontinuing, discontinued or not available, or whose supplier is archived, are never made preferred (skipped silently).

## The group Supplier Products page of an agent supplier has the same copy buttons
Vika, 18 Nov 2026. grp.supply-chain.suppliers.supplier_products.index shows Add products from another supplier, Add to another supplier and New supplier with these products when the supplier belongs to an agent the user may edit. Both pages build their props with CopySupplierProductsToSupplier::getCopyProductsProps/getCopyTargetsProps and render resources/js/Components/Procurement/SupplierProductsCopyActions.vue. The group page posts supplier_products ids (not org_supplier_products): an agent's supplier products have no org row in the agent organisation, only in client organisations, so never map them to org rows. CreateSupplier and StoreSupplier accept supplier_products for the same reason.

## Free suppliers share products through the same copy action
Vika, 18 Nov 2026. The group Supplier Products page of a free supplier (agent_id null) has the same three copy buttons when the user has supply-chain.edit. getCopyProductsProps then lists free suppliers as agent FREE_SUPPLIERS_KEY (0, create route grp.supply-chain.suppliers.create) beside the editable agents, posts to grp.models.supplier.supplier_products.copy (CopySupplierProductsToSupplier::inGroup) and reads sources from grp.json.supplier.supplier_products_to_copy_in_group. Copy targets of a free supplier are free suppliers plus editable agents' suppliers; an agent supplier's page still offers only agents' suppliers. CreateSupplier/StoreSupplier take supplier_products from free suppliers too (copyableSupplierProducts).
